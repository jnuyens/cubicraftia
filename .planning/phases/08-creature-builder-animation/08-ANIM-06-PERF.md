## Part 1 — Desktop FPS Smoke Measurement

### Environment

| Field                | Value                                                      |
|----------------------|------------------------------------------------------------|
| Host machine         | macOS 25.5.0 (Darwin) — Apple Silicon (M-class, ARM64)     |
| Godot version        | 4.6.3.stable.official.7d41c59c4                            |
| Renderer             | headless (no display, no GPU — mobile renderer enforced project-wide) |
| Run date             | 2026-06-09                                                 |
| Harness              | tests/perf/anim_frame_budget.gd (Plan 08-03, Option A headless fallback) |

### Method (Option A — headless fallback sub-case)

The benchmark scene (`src/world/benchmark_scene.tscn`) does not currently spawn the
creature roster, and creature `.glb` assets do not load headlessly (GLTFDocument
requires a rendering context for mesh import). Therefore this measurement exercises
the **procedural fallback path only** — `ProceduralCreatureAnimator.update()` called
per creature per frame. This is the dominant per-frame CPU cost for all single-mesh
TripoSR creatures (~18 of the 23 in the roster). The GPU-side cost of
`ShaderWobbleAnimator` (fish/ghost) and `MinifigureAnimator` rig updates is excluded;
their CPU overhead is a single uniform write per animator frame, negligible relative
to the transform path.

Measurement procedure:

1. Instantiate 23 `Node3D` mesh-root stand-ins (no mesh, transform-only) and one
   `ProceduralCreatureAnimator` (Motion.LAND) per stand-in, matching the worst-case
   roster of all creatures within the 40 m LOD radius at ~20 m from the builder.
2. Run 200 warmup frames (animated) to stabilise GDScript JIT bytecodes.
3. Sample 1000 frames animated: bracket each frame's `update()` block with
   `Time.get_ticks_usec()` for sub-millisecond resolution.
4. Run 1000 frames static baseline: same loop structure, `update()` calls omitted
   (measures loop + call overhead with no sin/cos/transform work).
5. Compute: animated average, static average, delta, and per-creature cost.

### Results

| Metric                               | Value                |
|--------------------------------------|----------------------|
| Creature count                       | 23                   |
| Sample frames                        | 1000                 |
| Animated average (23 creatures)      | 0.0201 ms/frame      |
| Static baseline (loop only)          | 0.0004 ms/frame      |
| Delta (animated - static)            | 0.0197 ms/frame      |
| Per-creature added cost              | 0.00085 ms/creature  |
| Animated p95                         | 0.0210 ms/frame      |
| Animated p99                         | 0.0210 ms/frame      |

Raw frame-time CSV: `user://benchmarks/anim-06-desktop.csv` (generated by harness,
written to the Godot user data directory on the dev machine).

### Verdict (Desktop / Procedural-Fallback Path)

PASS — per-creature cost is **0.00085 ms/creature**, well under the CONTEXT.md
target of **< 1 ms/creature** (margin: ~1180x). The full 23-creature roster adds
~0.020 ms/frame on this dev machine. At the Tier-3 frame budget of 33.3 ms/frame
(30 FPS cap), the animation roster consumes approximately 0.06% of the frame budget.

Scope note: this measurement covers the CPU transform path (ProceduralCreatureAnimator)
which is the dominant path for ~18 of 23 creatures. The remaining 5 creature types
(vampire: MinifigureAnimator CPU limb math; ghost: ShaderWobbleAnimator GPU uniform)
are expected to have comparable or lower CPU cost; they are excluded from this
headless harness because their rigged animators require a GPU context to initialise.
The Tier-3 hardware run (Part 2) covers all paths end-to-end.

## Part 2 — Tier-3 Reference Device Benchmark

### Status: DEFERRED — hardware-gated

This leg of ANIM-06 is deferred, mirroring the existing v1.0 Tier-3 hardware debt
(see STATE.md Deferred Items — "Phase 01 — 01-HUMAN-UAT.md (3 open scenarios):
partial — pre-launch hardware UAT" and "Verification Phase 01 — 01-VERIFICATION.md:
human_needed — Motorola Tier-3 benchmark + 5 platforms").

The authoritative §7.2 Tier-3 frame-budget check requires:
- Physical **Motorola One Macro (XT2016-1)** reference device
- USB debugging enabled, device connected to mains power
- `adb` installed on the host machine
- Android export template installed for Godot 4.6.3

These are not available in the executor environment. Instructions for discharge below.

### How to run the Tier-3 benchmark

From the repository root, with the Motorola One Macro connected via USB:

```
bash scripts/run-benchmark.sh
```

Wait approximately 31 minutes (do not touch the device during the run). The script:

1. Checks for adb + connected device.
2. Exports the Android APK using `benchmark_scene.tscn` as the main scene
   (via a temporary `override.cfg`).
3. Installs the APK on the device and starts the 30-minute thermal loop.
4. Pulls the CSV from `user://benchmarks/` via adb.
5. Calls `scripts/analyse-benchmark.sh` and prints PASS or FAIL with the
   worst-30-second-window min-FPS over the last 10 minutes vs. the 30 FPS threshold.

Pass threshold: **worst-30s-window min-FPS >= 30 FPS** over the last 10 minutes
of the run (§7.2 Tier-3 contract from DOCS.md).

Note: the stock `benchmark_scene.tscn` exercises terrain + builder + dynamite macro,
not the creature roster. The animation-specific evidence from Part 1 (desktop smoke
delta 0.00085 ms/creature) serves as the animation-specific signal. The Tier-3 run
establishes the frame-floor for the full game scene on low-end hardware.

Prerequisites summary:
- Device: Motorola One Macro (XT2016-1) — model XT2016-1
- USB debugging on, mains power connected
- `adb devices` confirms device is listed
- Android export template for Godot 4.6.3 installed
  (see `docs/MOTOROLA_BENCHMARK.md` for troubleshooting)
