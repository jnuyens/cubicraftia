# Phase 5 — UI Design Contract

> Covers every user-facing surface introduced or modified in this phase (DOC-08).
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.

**Source authority:** DOCS.md §8, 05-CONTEXT.md, 04-UI-SPEC.md (approved).
All upstream decisions are pre-populated. No design-system questions were re-asked.

## Spacing Scale

Inherited verbatim from Phase 4 UI-SPEC. No new tokens required.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap inside modal rows, radio button spacing |
| sm | 8px | Button row gap, report category item separation |
| md | 16px | Panel content margin, form field vertical spacing |
| lg | 24px | Section separation inside modals |
| xl | 32px | Reserved — not used in Phase 5 surfaces |
| 2xl | 48px | Bottom-sheet peek height (inherited from slide-in panels) |
| 3xl | 64px | Mobile touch targets for existing overlay buttons |

**Exceptions for Phase 5:**
- **Age gate date-of-birth picker row:** 3 dropdowns in an HBoxContainer with 8px (sm) gap between them. The combined row is at least 44px tall (mobile touch target minimum per DOCS §7.6).
- **Report category radio items:** 48px minimum touch target row height (same pattern as friend rows in Phase 4 friends panel).
- **Restricted-account banner:** 32px height, full-width, anchored to the top of the HUD CanvasLayer below the safe area. No content margin; the label is centred.

## Surfaces Specification

### NEW Surface A: Block Confirmation Modal

**Entry points:**
- Long-press (500 ms hold) on a friend row in the Friends panel — context menu appears.
- Long-press on a player nameplate in the world — context menu appears.
- The context menu item "Block" opens this modal.

**Layout:** `PanelContainer` centred at viewport centre. Fixed width: 400px desktop, full-width minus 32px horizontal margin on mobile. Auto-height. Modal overlay behind it: full-screen ColorRect, dominant navy `#1B2C56` at 60% alpha, `mouse_filter = MOUSE_FILTER_STOP` (taps outside do not dismiss; user must choose Confirm or Cancel).

**Content (top to bottom, 16px content margin, 16px (md) vertical separation):**
1. Heading: "Block {username}?" — Heading 20px semibold, brick white. `{username}` is injected at runtime.
2. Body: "They won't see you or your world. You won't see them." — Body 16px regular, brick-white 80% alpha. Max 2 lines, auto-wrap.
3. Button row (HBoxContainer, 8px gap, centred):
   - "Block" button — 160px wide, `StyleBox_button_destructive` (brick red fill). Label: "Block {username}".
   - "Cancel" button — 160px wide, `StyleBox_button_secondary` (border-only). Label: "Cancel".

**Behaviour:**
- Tapping "Block" calls `FriendsClient.block_user(uid)`, closes modal, emits `user_blocked(uid)` signal.
- `FriendsClient` removes the blocked user from the rendered friends list client-side immediately.
- Confirmation toast shown at top for 3 seconds: "You blocked {username}." Toast border: destructive red.
- Tapping "Cancel" closes modal with no action.
- The modal cannot be dismissed by tapping outside or pressing Escape — both buttons must be used.

**i18n keys (new for Phase 5):**
```

ui.block.body
ui.block.confirm_action
ui.block.cancel
ui.block.toast_blocked
```

### NEW Surface B: Report Flow (2-step modal)

**Entry points (three surfaces per DOCS §8.2):**
- Friends panel / nameplate context menu → "Report {username}" → `surface = 'player'`
- Long-press (500 ms) on a chat message row in ChatOverlay → "Report this message" → `surface = 'chat_message'`
- Long-press (500 ms) on a player nameplate (in-world) → "Report player" → `surface = 'player'`

**Step 1 — Category picker:**

Layout: same modal chrome as Surface A (PanelContainer, 400px / full-width-minus-32px, centred, 60% navy overlay). Content margin: 16px. Vertical separation: 16px between sections, 8px between radio items.

Content:
1. Heading: "Report {username}" (or "Report this message" for `chat_message` surface) — Heading 20px semibold, brick white.
2. Subheading: "What's the problem?" — Label 14px semibold, brick-white 70% alpha.
3. Radio button group (`VBoxContainer`, 8px separation). Each row is 48px tall (touch target). Five categories:
   - "Harassment or threats" — `ui.report.category_harassment`
   - "Spam or fake content" — `ui.report.category_spam`
   - "Cheating" — `ui.report.category_cheating`
   - "Child safety concern" — `ui.report.category_csam`
   - "Something else" — `ui.report.category_other`
   Radio buttons: Godot `CheckButton` in exclusive group. Label: 16px body, brick white.
4. Button row: "Next" (primary, full-width) disabled until a category is selected. The "Next" button uses `StyleBox_button_normal` styling with 0.5 alpha when disabled.
5. "Cancel" text button — 14px label, brick-white 60% alpha, centred below the Next button. No border, no background. Closes modal.

**Step 2 — Free-text reason + submit:**

Same modal chrome (replaces Step 1 content; no separate scene required — swap the VBoxContainer children).

Content:
1. Heading: "Add details (optional)" — Heading 20px semibold, brick white.
2. `TextEdit` node — 100% width, minimum height 96px (3 lines). Placeholder: "Describe what happened…" (16px body, brick-white 40% alpha). Max characters: 500. `max_length` via GDScript character counter since `TextEdit` does not natively enforce `max_length`. Word-wrap enabled.
3. Character counter: Label 14px, brick-white 50% alpha, right-aligned below the TextEdit. Format: "{n}/500". When remaining < 50: color changes to destructive red.
4. For `chat_message` surface only: a read-only display of the reported message and up to 5 messages of context, shown in a `PanelContainer` (navy 50% alpha, 8px padding, 96px max height, scrollable) above the TextEdit. Label 14px, brick-white 70% alpha, italic.
5. Button row (HBoxContainer, 8px gap):
   - "Submit report" — primary style, expand fill. Always enabled (reason is optional).
   - "Back" — secondary style, 120px. Returns to Step 1.

**On submit:**
- `FriendsClient.submit_report(surface, category, reason, evidence)` called.
- Modal closes.
- Confirmation toast at top of screen for 4 seconds: "Report submitted. Our team will review." Toast border: 1px brick-white (neutral, not destructive — reporting is a safety action, not inherently negative).
- Reported user is auto-muted locally for the remainder of the session (display filter, not a block). No notification shown for the auto-mute; it is silent.

### NEW Surface C: Age Gate Panel at Sign-up

**Trigger:** Replaces the existing `_age_checkbox` (CheckBox "I am 13 or older") in `sign_in_panel.gd` on the "Create account" tab. The checkbox is removed; a date-of-birth picker row replaces it, positioned between the password field and the submit button.

**Date-of-birth picker row:** `HBoxContainer`, 8px gap, items:
- "Day" `OptionButton` — 72px wide, values 1–31.
- "Month" `OptionButton` — 120px wide, values "January"–"December" (localised via i18n month keys).
- "Year" `OptionButton` — 96px wide, values (current_year − 100) to current_year in descending order. Initial selection: blank/"Year".
- All three start unselected (placeholder text "Day" / "Month" / "Year").
- Combined row minimum height: 44px.

**Under-13 detection:** Calculated client-side at submit time. If `birth_date + 13 years > today` (i.e., the declared age is under 13): the raw date of birth is NOT sent to the server (GDPR minimum-data principle per CONTEXT Area 3). Instead, the flag `is_under_13 = true` is sent in the GoTrue user metadata. The UI transitions directly to the Parental Consent Panel (Surface D) after successful account creation.

**Age gate validation error states:**
- DOB not fully specified: "Please enter your date of birth." (destructive red label, 14px, below the DOB row, matches the existing `_error_label` pattern).
- DOB is clearly impossible (e.g., day 31 for February): "Please enter a valid date." Same label, same style.
- Error label uses the existing `_error_label` node in `sign_in_panel.gd` — no new node required.

**13+ flow:** On submit with 13+ age, sign-up proceeds identically to Phase 4 behaviour. The age checkbox is gone; the DOB row implicitly captures the "I am 13 or older" declaration in the metadata.

### NEW Surface D: Parental Consent Panel

**Trigger:** Shown immediately after a successful account creation when `is_under_13 = true`. Also accessible from the restricted-account banner (Surface F) via "Resend email" → leads the user back here.

**Content (top to bottom):**

2. Body paragraph: "You'll need a parent or guardian to approve your account before you can play with friends. Enter their email address and we'll send them a confirmation link." — Body 16px regular, brick-white 80% alpha, centre-aligned, auto-wrap.
3. `LineEdit` — "Parent or guardian's email" placeholder, 16px body. Full-width. `keyboard_type = LineEdit.KEYBOARD_TYPE_EMAIL_ADDRESS`.
4. "Send link" button — primary style, full-width.
5. "Why am I seeing this?" — `LinkButton` or styled `Button` (no background, no border). Label: 14px, brick-yellow accent colour. On press: toggles a collapsible explanation panel (VBoxContainer, 8px padding, navy 50% alpha background, rounded 8px). Explanation text: "Cubicraftia asks players under 13 for a parent's permission before they can join sessions or chat with friends. Your parent's email is only used to send this confirmation — it is not stored after they confirm." Body 14px, brick-white 80% alpha. Auto-wrap.
6. "Skip for now" — `Button`, secondary style (border-only), full-width. On press: closes panel, shows restricted-account banner (Surface F). The under-13 account remains restricted.

  - Heading: "Link sent!" — Heading 20px semibold, brick white.

  - "Done" button — secondary style, centred 160px. Closes panel, shows restricted-account banner.
  - "Resend" — `LinkButton` 14px, brick-yellow. On press: re-sends and shows brief "Sent again." toast (2 seconds, no border, top of screen).
- On network failure: "Could not send the email. Check your connection and try again." (destructive red label below button, button re-enables).

### NEW Surface E: EULA + Privacy Viewer

**Entry points:**
- Title screen: two small `LinkButton`-styled labels in the bottom-left corner of the title screen (`CanvasLayer` layer 10), always visible. Labels: "Terms of Use" and "Privacy Policy". 14px label weight, brick-white 60% alpha. On hover: 100% alpha.
- Settings menu → "About" section → "Legal" subsection (see Surface J modification).

**Layout:** Full-screen `CanvasLayer` (layer 15 — above the title screen, below modals at 20+). Single `PanelContainer` centred, 560px wide on desktop, full-width minus 32px on mobile. Fixed height: 80% of viewport height. Background: dominant navy at 0.95 alpha, rounded 16px corners.

**Content (top to bottom, 16px content margin):**
1. Panel header bar (HBoxContainer, 48px height):
   - Title label: "Terms of Use" or "Privacy Policy" (injected at open) — Heading 20px semibold, brick white. `SIZE_EXPAND_FILL`.
   - "Close" Button — secondary style, 80px wide, right-aligned. Label: "Close".
2. `ScrollContainer` — fills remaining height (`SIZE_EXPAND_FILL`). Vertical scroll only.
   Inside the scroll: a `VBoxContainer` of `Label` nodes rendered from the Markdown content. Markdown parsing rules:
   - `# H1` → Label, 20px semibold (Heading rung).
   - `## H2` → Label, 16px semibold (Body rung + `add_theme_font_size_override` to 16px + bold weight flag).
   - `**bold**` → inline: use `RichTextLabel` instead of bare `Label` for this section, with `bbcode_enabled = true`, `fit_content = true`.
   - Plain paragraphs → Label, 16px regular, auto-wrap, `SIZE_EXPAND_FILL`.
   - Unordered list items → Label with "• " prefix, 16px regular, 16px left margin.
   - Inline links → ignored in Phase 5 (no URL rendering in-game for legal text links).
   The plain-language summary block (3–5 bullets at the top of each document) is wrapped in a `PanelContainer` with `StyleBox_legal_summary` (see new StyleBox below).
3. Footer bar (HBoxContainer, 40px height, top border 1px brick-white at 20% alpha):
   - Version hash label: "Version: {first 16 hex chars of SHA-256 hash}" — Label 14px, brick-white 40% alpha. Left-aligned.
   - "I agree" Button — primary style, 160px wide, right-aligned. **Only visible on first view or on re-acknowledge flow.** Hidden after the user has already agreed to this version.

**EULA re-acknowledge flow:** On app launch, if `user://settings.cfg [legal] eula_hash` differs from the bundled EULA hash: a modal (PanelContainer, 400px, centred, navy overlay) is shown before the title screen:
- Heading: "We updated our Terms of Use" — Heading 20px semibold.
- Body: "Please review and accept the new terms to continue." — Body 16px.
- "Review Terms" Button — primary style, full-width. Opens EULA Viewer with "I agree" button visible.
- "Sign out" Button — secondary style, full-width. Signs the user out and returns to title (account remains).
- The modal cannot be dismissed without choosing one option.

**On "I agree" press:** Writes `eula_hash` to `user://settings.cfg [legal]`, closes the viewer (or dismisses the re-acknowledge modal). Shows no toast (acceptance is not a celebration).


## Verdict

**APPROVED-WITH-RECOMMENDATIONS**

The design contract is complete and internally consistent. All 7 new surfaces and 5 modifications are fully specified with layout, typography, color, interaction, and i18n keys. No design-system questions require user input — all decisions flow from upstream artifacts.

**Recommendations before executor starts:**

1. **Context menu singleton (performance):** The context menu (`PanelContainer`, 160px) appears in three surfaces (friend row, chat message, nameplate). Implement it as a single autoloaded scene (`src/ui/context_menu.gd`) rather than instantiating per row. The executor should design the API: `ContextMenu.show(items: Array[Dictionary], screen_pos: Vector2)` where each item is `{label: String, action: Callable}`. This avoids 40+ simultaneous `PanelContainer` instances in the chat history.

2. **DOB year OptionButton depth:** The OptionButton with ~100 years of values is known to have scroll-lag on Tier-3 Android. Mitigations: (a) limit year range to `current_year - 13` downward by 100 (only years where the user could be ≤ 13 + 100 years back are needed; practically any valid human age); (b) if perf is poor on Tier-3, replace with a `LineEdit` number input for year only (less polished, but 0 scroll lag). Flag this as a Tier-3 perf spike item in the planning phase.

3. **EULA markdown parser scope:** The `RichTextLabel`-based renderer is acceptable for Phase 5 (EULA is < 5KB). Do not implement a full Markdown parser — handle the six constructs listed (H1, H2, bold via bbcode, plain paragraphs, unordered lists, the summary box). Anything more complex in the legal text should be rewritten as plain text before bundling.

4. **Profanity filter on username field:** The 500ms inline validation (green checkmark or red error) must NOT fire a network request — it is format-only. The uniqueness and reserved-prefix checks happen only on submit. This prevents information leakage (a bad actor enumerating taken usernames in real time). The executor must not add a `search_friend`-style debounced HTTP call for the inline username validator.

5. **Under-13 DOB raw value:** The DOB dropdowns collect day/month/year but only `is_under_13: bool` is sent to the server. The raw DOB must never appear in any log, analytics event, or Supabase column. The executor should confirm this at the `FriendsClient.sign_up()` call site.
