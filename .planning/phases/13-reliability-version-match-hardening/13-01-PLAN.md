<objective>
Add the shared "connection problem" reason plumbing to NetworkManager (D-01/D-02), wire the
previously-silently-ignored Go signaling `"error"` message type into that plumbing, and add
the two bounded-timeout mechanisms that make the "Connecting..." and failover-reconnect states
non-frozen (D-03, D-04): the initial-join CONNECTING_TIMEOUT_S (RELY-03) and the failover
FAILOVER_RECONNECT_TIMEOUT_S grace window (RELY-02, reusing STATE_RECONNECTING per D-03).

Purpose: this is the backbone every other Phase 13 plan (UI overlay, JoinScreen, version-match
gate) depends on — one signal, one set of canonical reasons, no more silent hangs.
Output: `connection_problem(reason)` signal + `report_connection_problem()` public API on
NetworkManager; two new bounded timers; 3 new GUT test files.
</objective>

over the SAME WebSocket that `_on_signaling_message()` already parses. Confirmed existing codes
(grep `signaling-server/internal/hub/hub.go` / `relay.go`):
  - `"blocked"` — join rejected, block relationship exists (hub.go:287,291)
  - `"session_full"` — session has reached MAX_PEERS_PER_SESSION (hub.go:310)
  - `"peer_not_found"` — target UID (host) is not currently connected (relay.go:26) — fires
    when a joining peer's "offer" cannot be relayed because the host is gone
  - `"version_mismatch"` — Go relay wire-protocol "v" field mismatch (hub.go:170) — DISTINCT
    layer from the new gameplay PROTOCOL_VERSION (added in Plan 13-04), but both are genuine
    "your build cannot talk to this session" cases; per D-01 (one reason enum, not N dialogs)
    both map to the client's single `version_mismatch` reason.
  - `"consent_required"` — under-13 unconsented join (hub.go:300,304) — this is the EXISTING
    `join_blocked("parental_consent_required")` flow (ParentalGatePanel); do NOT route this one

  - All other codes (`bad_payload`, `parse_error`, `unknown_type`, `peer_limit_exceeded`,

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Go signaling server → client | Untrusted-by-default WebSocket messages (server is trusted infra, but message content drives client-side UX branching) |
| Peer WebRTC connection state → client UI reason | Locally-observed connection state, not attacker-controlled, but drives which reason string the player sees |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01-01 | Information Disclosure | `_on_signaling_message` "error" mapping | accept | Only whitelisted codes map to a reason string; all other codes are logged via `push_warning` server-side detail only, never surfaced to the player UI (no raw Go error message text reaches `connection_problem`) |
| T-13-01-02 | Denial of Service | `_connecting_timeout_timer` / `_reconnect_grace_timer` | mitigate | Both timers are one-shot with fixed bounded durations (12s / 5s) — a stalled/attacker-delayed handshake can never hang the client past these bounds |
| T-13-01-03 | Tampering | Unknown/unexpected signaling error codes | mitigate | `match` statement's default arm only `push_warning()`s; it never calls `report_connection_problem()` with an attacker-influenced free-text string, preventing message-injection into the overlay |
</threat_model>
