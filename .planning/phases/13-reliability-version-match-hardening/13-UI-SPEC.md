# Phase 13 — UI Design Contract

> Visual and interaction contract for Phase 13: Reliability & Version-Match Hardening.
> Covers RELY-01..05 and VER-01..02's user-facing surface: one reusable
> "connection problem" overlay, the non-frozen connecting/reconnecting states,
> and a relay-vs-direct connection badge. This is functional system UI, not a
> marketing surface — the contract below is deliberately small and reuses the
> existing Phase 4 chrome/theme wholesale.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.

**Source authority:** 13-CONTEXT.md (D-01..D-10), FEATURES.md (v1.2 connection-failure
taxonomy), `network_manager.gd`, `network_hud.gd`, `join_screen.gd`,
`assets/themes/cubicraftia.tres`. No design-system questions were re-asked — this
phase adds zero new StyleBoxes, zero new spacing tokens, and at most one new icon
asset (see below), all pre-populated from the Phase 4 UI-SPEC precedent.

## Surface A: Connection-Problem Overlay

**New component.** One reusable, reason-driven modal. Not per-reason dialogs.

### Trigger

Shown exclusively when `NetworkManager.connection_problem(reason: String)` fires.
`host_failover_failed(reason)` and `join_blocked(reason)` are forwarded into
`connection_problem` by NetworkManager (D-02) — the UI layer has exactly one signal to
listen to, regardless of which underlying failure produced it.

### Structure

```
ConnectionProblemOverlay   (CanvasLayer, layer = 110)
└─ Overlay                 (ColorRect, full-rect, navy #1B2C56 @ 0.88 alpha)
   └─ Content               (VBoxContainer, centred, max-width 400px, separation 16px)
      ├─ Icon               (TextureRect, 32×32, icon_error.png upscaled, brick-white tint)
      ├─ Heading             (Label, 20px semibold, #D63828)
      ├─ Body                (Label, 16px regular, #F1F0EA, autowrap)
      └─ ButtonRow           (HBoxContainer, separation 8px)
         ├─ PrimaryButton    (Button, 160px, StyleBox_button_normal)
         └─ SecondaryButton  (Button, 160px, StyleBox_button_secondary — only present
                               for reasons that declare a secondary action)
```

**Layer rationale:** 110 — one above the Handover Screen's layer 100 (Surface 9,
04-UI-SPEC.md). The overlay must be able to supersede an in-progress "Switching
host…" screen (e.g. failover elects a peer, then that peer's promotion itself times
out) as well as anything shown by `JoinScreen` (layer 20) or the in-game HUD.

**Single-button layout:** for reasons with no secondary action, `SecondaryButton` is
not instanced; `PrimaryButton` is centred alone (`size_flags_horizontal = SHRINK_CENTER`
on the `ButtonRow`, or simply omit the `HBoxContainer` wrapper and place the single
button directly in `Content`).

### Reason → Message → Action Table

All 7 reasons share the **same heading** ("Couldn't connect") — only the body and
action set change per reason. This is deliberate: a shared heading means the `blocked`
reason is never visually distinguishable from any other failure at a glance, which
reinforces the fail-closed, non-revealing requirement below.

| Reason | Body copy intent (EN) | Primary action | Secondary action | i18n key (body) |
|--------|------------------------|-----------------|-------------------|------------------|
| `expired` | Invite link is stale/single-use-expired; direct the player to ask the host for a fresh one. No retry (retrying an expired token never succeeds). | Back to menu | — | `ui.connproblem.reason_expired` |
| `full` | Session already has 4/4 builders. No retry (won't resolve itself in the moment). | Back to menu | — | `ui.connproblem.reason_full` |
| `ended` | Session no longer exists (host closed it, or it ended before the join completed). | Back to menu | — | `ui.connproblem.reason_ended` |
| `blocked` | **Generic, non-revealing.** Never states or implies "you are blocked" (fail-closed pattern already used for COPPA/block gates elsewhere in the codebase — this phase extends that principle to the invite-link surface). Reads identically to a garden-variety failure. | Back to menu | — | `ui.connproblem.reason_blocked` |
| `version_mismatch` | Local build's `PROTOCOL_VERSION` differs from the host's. Tells the player to update; **never shows the raw integer version numbers** (that's an internal build-compat detail, not player-facing information) and does **not** offer an "Update" button in Phase 13 — the update-check UX is DIST-05 (Phase 15), out of scope here. | Back to menu | — | `ui.connproblem.reason_version_mismatch` |
| `relay_failed` | TURN relay itself failed, or the network is restrictive enough that no path (direct or relayed) succeeded. Genuinely retryable. | Retry | Back to menu | `ui.connproblem.reason_relay_failed` |
| `timeout` | The bounded Connecting/Reconnecting window (RELY-02/03) elapsed with no resolution. Genuinely retryable. | Retry | Back to menu | `ui.connproblem.reason_timeout` |

**`{host}` interpolation:** where the body copy references the host by name (`expired`,
`version_mismatch`, `relay_failed`), resolve via the same pattern `JoinScreen` already
uses (`SessionRegistry.get_host_uid()`), falling back to the generic "your host" /
"je host" string if unresolved — do not add a second host-name-resolution helper.

### Modal / Focus / Input Behavior

- The `Overlay` `ColorRect` has `mouse_filter = MOUSE_FILTER_STOP` — no click passes
  through to gameplay or any panel underneath.
- On show: force `Input.MOUSE_MODE_VISIBLE` (mirrors the existing Esc-releases-mouse
  convention in `main_scene._unhandled_key_input`) so the player can click the button(s)
  even if RMB camera-look had the mouse captured.
- On show: `PrimaryButton.grab_focus()` is called immediately, so `Enter`/gamepad-equivalent
  activates the primary action with zero mouse movement required.
- **Not dismissible by Escape key and not dismissible by clicking the scrim.** The only
  way to close the overlay is pressing one of its own buttons. This is a deliberate
  design choice — unlike the Settings menu (Esc always works) or the non-actionable
  Handover Screen (nothing dismisses it, it auto-resolves), a connection problem
  represents a state the player must explicitly acknowledge and act on.
- **Never auto-dismisses.** Unlike the Handover Screen (Surface 9), which listens for
  `host_failover_complete` and free itself, `ConnectionProblemOverlay` only ever closes
  via a button press.

### Button Behavior

- **Retry** (`relay_failed`, `timeout` only): hides the overlay, re-invokes the same
  connection attempt that was in progress (re-run `start_peer`/reconnect entry point for
  that context — the exact NetworkManager call is planner/executor scope). If the retry
  is in a join context, `JoinScreen`'s Connecting content (Surface B below) reappears
  while the retry is attempted.
- **Back to menu**: hides the overlay, ends the session cleanly (`begin_graceful_disconnect()`
  if a session is active), and returns to the main/title flow — the same destination
  `JoinScreen`'s existing `BackButton` already reaches via `queue_free()`.

### Migration Note (JoinScreen)

`JoinScreen._show_error(reason)` and its `ErrorContent` / `ErrorHeading` / `ErrorBody` /
`BackButton` nodes are **removed**. `JoinScreen`'s `STATE_DISCONNECTED` handler (and any
future reason-bearing failure path) delegates to `ConnectionProblemOverlay.show_reason(reason)`
instead of toggling its own local nodes. This is required to satisfy D-01 ("ONE reusable
overlay... NOT N ad-hoc dialogs") — without this removal, the codebase would have two
competing error-rendering surfaces.

The existing locale keys `ui.join.error_session_full`, `ui.join.error_expired`, and
`ui.join.error_connection` are **superseded** by `ui.connproblem.reason_full`,
`ui.connproblem.reason_expired`, and `ui.connproblem.reason_relay_failed`/`reason_timeout`
respectively. Remove the old keys from `locale/en.po`/`locale/nl.po` once `JoinScreen`
no longer references them (do not leave orphaned msgids). `ui.join.error_unverified_session_age`
is unaffected — it is a distinct, already-shipped gate (session-age verification), not
one of the 7 reasons in this phase's enum.

## Surface B: Connecting / Reconnecting States

**Extends the existing `JoinScreen` Content block** (`Overlay/Content` — Heading +
StatusLabel). No new scene; one node added.

### Connecting state (RELY-03 — `STATE_CONNECTING`)

The existing `JoinScreen.tscn` header comment claims a spinner ("Spinner:
AnimatedSprite2D, icon_spinner, 2 Hz") but **no such node exists in the current scene
file** — only `Heading` and `StatusLabel` are present. Phase 13 must add it; this is a
gap this UI-SPEC exists partly to close.

Add, between `Heading` and `StatusLabel`:

```
Spinner   (AnimatedSprite2D, 32×32, icon_spinner.png — 4-frame spritesheet, 2 Hz)
```

This is a straight reuse of the exact spinner asset and animation rate already defined
for the Handover Screen (Surface 9) — do not create a second spinner asset or a
different frame rate.

- Heading: `ui.join.heading` ("Joining {username}'s world…") — unchanged.
- Spinner: always playing while this state is visible. Never a `ProgressBar` (indeterminate
  progress bars remain banned on Tier-3 per the existing performance note).
- Status label: `ui.join.status_connecting` ("Connecting…") — unchanged.
- **Bounded timeout (10-15s const, exact value is a code constant, not a UI decision):**
  on timeout, `NetworkManager` emits `connection_problem("timeout")`. `JoinScreen` hides
  its `Content` block; `ConnectionProblemOverlay` shows the `timeout` reason. There is no
  indefinite hang state — every path out of Connecting is either success or a shown reason.

### Reconnecting state (RELY-02/03 — `STATE_RECONNECTING` / `STATE_FAILOVER_WAITING`)

Two distinct cases exist; they must not be conflated:

1. **Brief blip during an active session** (RELY-02, D-03): the auto-reconnect grace
   window (~5s tunable const) is **silent by design — no visible UI change of any kind**
   for the entire window, not merely for the first fraction of a second. If reconnection
   succeeds before the window elapses, the player never sees anything (no toast, no HUD
   change, no overlay). This is intentional: it's the difference between RELY-02
   (silent-unless-it-fails) and RELY-03 (always-visible Connecting state for the initial
   join). Do not add a subtle "reconnecting" HUD chip for this case — that would
   contradict "SILENT" in D-03.
   - **Only if the grace window elapses** does `NetworkManager` emit
     `connection_problem("timeout")` or `connection_problem("ended")` (the choice
     between these two reasons is a NetworkManager/backend decision, not a UI one — the
     UI already has both covered in the reason table above).

2. **Waiting for a new host during failover** (`STATE_FAILOVER_WAITING`,
   `STATE_RECONNECTING` while `JoinScreen` happens to still be present, e.g. failover
   during the initial join window): update the existing status label from
   `ui.join.status_loading` ("Loading world…") to the new key `ui.join.status_reconnecting`
   ("Reconnecting…") — more honest copy for what's actually happening. This is the one
   small copy correction in scope for this phase; it directly serves the "never frozen,
   always explained" goal of RELY-02/03.

**These two states never overlap with the Handover Screen (Surface 9).** Handover
already owns the "the host is gone, a new one is being elected" moment in full for
players who are already in-game; `JoinScreen`'s Reconnecting label only matters for a
peer who is mid-join when failover starts.

## Surface C: Relay-vs-Direct Connection Badge

**Extends the existing per-peer row in `NetworkHud`** (`network_hud.gd`/`.tscn`,
top-right HUD corner, 16px from top/right edges, per Surface 10 of 04-UI-SPEC.md — no
placement change).

### Current state → required state

Today, `NetworkHud.show_relay_badge(peer_id, show)` toggles a single `Label` ("Relay",
amber) that is hidden by default and only ever shown positively — direct connections
render nothing. RELY-05 requires an **honest, always-visible two-state indicator**
(FEATURES.md differentiator: "showing it sets expectations honestly" — hiding-by-default
undersells the one thing this badge exists to communicate).

Rename the concept from "show/hide a Relay badge" to "always show one of two labels":

| State | Label text | Color | i18n key |
|-------|-----------|-------|----------|
| Direct P2P | "Direct" | `COLOR_GOOD` (`Color(0.31, 0.87, 0.22, 1.0)`) | `ui.netstatus.badge_direct` (NEW) |
| TURN relay | "Relay" | `COLOR_AMBER` (`Color(0.91, 0.54, 0.05, 1.0)`) | `ui.netstatus.relay_badge` (EXISTING — unchanged key, keep for locale continuity) |

### Layout

No layout change: same `Label` node (`RelayBadge`, may be renamed `ConnectionBadge` at
the executor's discretion), same position (8px right of the username label, within the
existing 24px-tall peer row), same 12px font-size exception already granted in Surface
10. The only change is: `visible` is always `true` once a peer row exists (never
`false`), and the API becomes `set_connection_badge(peer_id: int, is_relay: bool)`
(replacing `show_relay_badge`) which sets both `.text` and `.modulate`/font color in one
call.

### Behavior

- **Informational only — non-interactive.** No click handler, no tooltip, no hover
  state. This must not become a button.
- **Update cadence:** matches the existing performance constraint for this HUD (Surface
  10) — updated only on ICE selected-candidate-pair change events, never per-frame and
  never on the 1Hz RTT timer tick (those are a different signal; conflating them would
  mean the badge lags or flickers on every RTT poll for no reason).
- **Scope boundary:** this badge's correctness under real relay/failover conditions is
  validated in Phase 12 (NETVAL-04) — Phase 13 only ships the always-on two-state UI and
  the wiring contract (`NetworkManager` reports which state per peer); it does not
  re-verify ICE candidate detection logic, which already exists.

## Acceptance Checkpoints

Explicit, testable checklist for `gsd-planner` (task breakdown) and `gsd-ui-checker`
(verification):

- [ ] `ConnectionProblemOverlay` is a single scene (`connection_problem_overlay.gd`/`.tscn`)
      driven by exactly one public entry point, `show_reason(reason: String)`, called
      only from a `NetworkManager.connection_problem` signal handler.
- [ ] All 7 reasons (`expired`, `full`, `ended`, `blocked`, `version_mismatch`,
      `relay_failed`, `timeout`) render distinct body copy from the table above; the
      heading is identical across all 7.
- [ ] The `blocked` reason's copy never contains the word "blocked" or any language
      implying the player was specifically excluded — verified by literal string review,
      not just i18n key presence.
- [ ] The `version_mismatch` reason's copy never renders a raw `PROTOCOL_VERSION`
      integer or git-sha.
- [ ] `relay_failed` and `timeout` show both Retry + Back to menu; the other 5 reasons
      show Back to menu only.
- [ ] The overlay cannot be dismissed by Escape key or by clicking its background scrim
      — only its own button(s) close it.
- [ ] `PrimaryButton.grab_focus()` is called every time the overlay becomes visible.
- [ ] `JoinScreen`'s old `ErrorContent`/`ErrorHeading`/`ErrorBody`/`BackButton` nodes and

- [ ] The auto-reconnect grace window (RELY-02) produces **zero** visible UI change for

- [ ] The Connecting state (RELY-03) times out to `connection_problem("timeout")` within

- [ ] `NetworkHud`'s connection badge is visible for every connected peer row at all

- [ ] The connection badge has no click handler, hover state, or tooltip.
- [ ] All new strings exist in both `locale/en.po` and `locale/nl.po`; no hardcoded
      English strings in any new/modified `.gd`/`.tscn` file.
- [ ] No em-dash or en-dash appears in any new Phase 13 string.
- [ ] Terminology check: "builder(s)" used for players (`full` reason copy), never
      "player(s)"; "session" never "lobby"/"game"; "brick"/"stud" untouched/untranslated
